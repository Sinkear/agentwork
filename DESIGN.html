AgentWork 架构与设计文档

一个面向多种 Agent Runtime 的任务管理、调度、协作、验收与交付控制平面。

Status: Vision / 规划愿景（非现状） Version: 1.0 Date: 2026-08 Runtime: Go Storage: SQLite
核心定义：AgentWork 不是“多 Agent Kanban”，而是一个让 Agent 能够持续、可靠、可验证、可恢复地完成工作的 Agent Execution Control Plane。Kanban、Cron、Issue、IM 都是外围入口；Goal、Run、Scheduler、Agent Session、Verification、Review、Delivery 才是核心闭环。
阅读说明：本文档是 架构愿景（目标态设计），不是现状基线。现状的权威是 DESIGN.md（决策 2-x / 3-x / 4-x 编号，代码注释引用它）；数据库结构以 internal/store/schema.sql 为准。本文描述的能力（AgentSession 统一抽象、Run Admission、worker lease、持久化 Event Log、Capability Token、Repository 层等）多数为规划未实现；与 DESIGN.md 冻结决策冲突处（§6 状态机、§7 Delegation、Roadmap）已就地标注。愿景与现状冲突时，以 DESIGN.md 与代码为准。

1. 设计目标与原则

1.1 目标

  • 统一管理 Coding、IaC、Research、Ops 等不同类型 Agent。
  • 将“任务事实”和“一次执行”分离，支持 retry、review、handoff、recovery。
  • 让人定义验收标准，Agent 执行，平台验证，人只在必要的 Gate 出现。
  • 支持本地 Agent、远程 Agent、不同 Runtime 与不同协议。
  • 支持 crash recovery、幂等交付、执行审计与实时 UI。
  • 通过统一 Goal 模型承接 Web、Cron、Issue、IM、Agent 等不同触发来源。

1.2 核心原则

原则含义
Goal 是事实业务任务的状态权威属于 Goal，而不是某个 Run。
Run 无状态权威Run 只描述一次执行；执行结果必须经过 Goal 层 reconcile。
定义、执行、判定分离Human/Domain 定义验收策略，Agent 执行，Platform/Processor 验证。
DB 是 TruthEvent Bus/WebSocket 只负责通知，不能成为事实来源。
Runtime 与业务解耦业务层只依赖 AgentSession，不直接依赖 ACP/JSONL/JSON-RPC。
Agent 不负责 DeliveryAgent 产生工作结果，平台负责 Review、Merge、Deploy 等交付动作。
外围能力 Adapter 化Cron、GitHub Issue、IM、PR/MR 等均通过 Trigger/Delivery Adapter 接入。
先简单、后分布式当前单机单用户优先 SQLite + 单 daemon，不提前引入 PostgreSQL/Temporal。

4. Goal

Goal 是系统最重要的业务实体，也是 UI、Scheduler、Agent、Review、Delivery 的共同连接点。

字段为愿景模型，与实际 schema 存在差异（现状含 handoff_note / human_iterations / source_ref / current_agent_id，无 priority / workspace_id / acceptance_policy_id）——以 schema.sql 为准。

Goal {
  id
  domain_id
  parent_id
  title
  description
  status
  priority
  assignee_agent_id
  workspace_id
  acceptance_policy_id
  created_at
  updated_at
}

4.1 Goal Aggregate

所有 Goal 状态变化必须经过 Goal 层统一 reconcile，禁止 Run、Agent、Delivery 直接修改 Goal 的终态。

RunCompleted
      │
      ▼
RunResult
      │
      ▼
Goal.Reconcile(result)
      │
      ├── completed
      ├── failed
      ├── review
      ├── blocked
      └── active

4.2 Parent / Child

父子 Goal 用于表达任务分解和 Agent delegation。当前阶段不引入独立 Workflow Engine；复杂流程优先用 parent_id + dependency + Goal State Machine 表达。

5. Run

Run 是一次具体执行。一个 Goal 可以有多个 Run。

字段为愿景模型（worker_id / claimed_at / lease_until 未实现——现状为 daemon restart 时全量 recover running→queued）；实际字段含 attempt / evidence / result_summary / trigger_comment_id，以 schema.sql 为准。

Goal
 ├── Run #1 → failed
 ├── Run #2 → review
 ├── Run #3 → failed
 └── Run #4 → completed
Run {
  id
  goal_id
  agent_id
  attempt
  status
  session_id
  trigger
  worker_id
  claimed_at
  lease_until
  started_at
  completed_at
  error
}
重要：Run 的完成、失败、取消只表示一次执行的结果。Goal 是否进入 done/review/failed 必须由 Goal Aggregate 根据 RunResult、Policy、Child Goals、Review 和 Delivery 状态统一决定。

6. Goal 状态机

                    ┌───────────┐
                    │  backlog  │
                    └─────┬─────┘
                          │ dispatch
                          ▼
                    ┌───────────┐
              ┌────►│   active  │◄──────┐
              │     └─────┬─────┘       │
              │           │              │
       retry/rework       │ candidate    │ reject
              │           ▼              │
              │     ┌───────────┐        │
              └─────│  review   │────────┘
                    └─────┬─────┘
                          │ approve
                          ▼
                    ┌───────────┐
                    │ delivery  │
                    └─────┬─────┘
                          │ success
                          ▼
                    ┌───────────┐
                    │   done    │
                    └───────────┘

active ──► blocked
active ──► failed
active ──► cancelled

blocked 表示系统无法继续；review 表示机器可以继续，但根据策略需要人或指定审批者决定。两者必须保持语义分离。

与现状差异：现状无独立 delivery 状态——approve 后平台执行 deliver（merge+re-verify+push），goal 保持 review 直至 MarkDelivered 才到 done；blocked 已随 wait-children 机制退役（决策 6-10，goal 状态机五态）；协作走四行为模型（决策 5-1/5-2）+ sub_goal 实体（决策 6-1：不可递归、依附 goal 生命周期、Change+Revision 交付）。

7. Squad & Delegation

Squad 不是执行池，而是 Agent 协作与路由组。Leader Agent 是实际的协作入口。

Squad
  │
  └── Leader
       ├── Agent A
       ├── Agent B
       └── Agent C

Parent Goal
     │
     ▼
Leader Agent
     │
     ├── create child Goal → Agent A
     ├── create child Goal → Agent B
     └── create child Goal → Agent C

Delegation 的本质是创建/更新 Goal，而不是在 AgentWork 内部偷偷执行一个不可见 Workflow。

本节已更新（决策 5-1 撤销 3-6，6-1 重定义）：child-goal 委派已以 sub_goal 实体落地——不是 child goal：不可递归、依附 goal 生命周期、assignee/verifier 分离、Change+Revision 跨 workspace 交付、owner 集成（详见 Collaboration.v2.md）。squad 仍以 leader run + role=reviewer 审查 checkpoint（决策 4-4）运作。

交接语义（决策 4-9）：goal 易主时平台终止旧 owner 的 running run（per-run cancel 注册表）——旧 agent 已交接却不结束 run，会把新 owner 的 run 永远堵在 per-goal 串行队列后（死锁）；AGENTWORK.md 同步引导"交接后立即结束你的 turn"。

9.2 Run Admission

所有 Run 触发入口必须统一经过 CanRun() / Admission。

  • Goal 是否允许执行。
  • 依赖 Goal 是否完成。
  • Agent 是否可用。
  • Agent concurrency 是否达到上限。
  • 是否存在同一 Goal 的 running Run。
  • 是否需要 Approval。
  • Workspace 是否可用。
  • Policy 是否满足。
  • Quota / Resource 是否满足。

9.3 Claim

Claim 必须是原子的。推荐通过数据库事务/条件 UPDATE 避免“先 SELECT 再 UPDATE”产生 race condition。

UPDATE runs
SET status = 'running',
    worker_id = ?,
    claimed_at = ?,
    lease_until = ?
WHERE id = ?
  AND status = 'queued'
  AND NOT EXISTS (
      SELECT 1 FROM runs
      WHERE goal_id = ?
        AND status = 'running'
  );

10. Workspace

Workspace 是 Agent 工作的物理执行边界。当前以 Git Worktree 为主要实现。

Domain Repository
 ├── workspace/goal-A
 ├── workspace/goal-B
 └── workspace/goal-C

同一 Goal 的多个 Run 通常复用同一个 Workspace，以支持 retry/rework。不同 Goal 默认隔离。

架构决策：业务层依赖 Workspace，不直接依赖 GitWorktree。GitWorktree 是 Workspace 的一个实现，为未来文档、知识库、IaC 状态等非 Git 资产留出空间。

11. Client RPC

远程 Agent 的关键不是“远程启动”，而是 Agent 访问其工作环境所需的 Client RPC。

Remote Agent
     │
     │ fs.read / fs.write / terminal / approval...
     ▼
AgentWork Client RPC
     │
     ▼
Goal Workspace / Runtime Context

Client RPC 是 AgentWork 的通用执行边界。现状（决策 4-8 已实现）为双通道：

  • ACP fs/terminal RPC——8 个 handler（read/write + terminal×5 + request_permission 自动放行），握手声明 clientCapabilities。
  • MCP 工作区 server——官方 go-sdk，streamable HTTP 挂在 /mcp/{runID}（GET+POST；GET 是 SSE 订阅，缺失会 405 导致工具不注册），session/new 的 McpServers 注入 URL。

统一模型：stdio/ws/tcp 同机制（注册 handler、声明能力、注入 Workspace 指引段——只说环境事实与协作契约，不指 agent 工具名）。遗留：fs 敏感文件拦截、MCP capability token（runID 即访问权）列后置。

13. Review / Gate

Review 是 Human-in-the-loop 的显式状态，不应被简单等同于 blocked。

Verification
    │
    ├── pass ──► auto delivery
    │
    └── requires human
              │
              ▼
            Review
          ┌───┴───┐
          ▼       ▼
       approve   reject
          │       │
          ▼       ▼
       delivery  active

Gate Decision 必须持久化，包含决策者、时间、决策、理由以及关联 Evidence。

14. Delivery

Delivery 是平台动作，不是 Agent 动作。

Agent
  ↓
implementation
  ↓
Verification
  ↓
Review
  ↓
AgentWork Delivery
  ├── local merge
  ├── GitHub PR
  ├── GitLab MR
  ├── deploy
  └── artifact publish

Delivery 应通过 Adapter 扩展。必须具备幂等性，例如重复执行 merge/push/deploy 时能够识别已经完成的动作。

15. Evidence

Evidence 是“为什么可以认为这个 Goal 已经完成”的机器可读证据集合。

类型示例
Diff文件变更、统计、关键 diff。
Test测试命令、退出码、输出、覆盖率。
QualityLint、Format、Static Analysis。
Security安全扫描、依赖扫描。
Agent Report结构化执行总结。
Screenshot/ArtifactUI、构建产物等。
Delivery ResultMerge/PR/Deploy 结果。

Review 的对象应是 Evidence，而不是 Agent 的一句“done”。

审批对象语义（决策 4-4）：被审批的是触发卡点的 owner run 的证据（agent 目标 = assignee 的 run，squad 目标 = leader run）——不能用“最新 completed”近似（审查 run 晚于触发 run 入队，会把审批对象错位成审查者）；reviewer 的审查意见是评论区的参考观点，不是被审批对象。审查 run 只读：不提交其 worktree 改动（残留走下一 run 脏检查安全失败）。

16. Event & Event Bus

系统事实应通过 Event 持久化；Event Bus 负责异步通知。

Event {
  id
  type
  aggregate_type
  aggregate_id
  payload
  created_at
}

典型事件：

goal.created
goal.assigned
run.created
run.started
run.completed
run.failed
review.requested
gate.approved
gate.rejected

原则： DB = Truth；Event Bus = Notification；WebSocket = UI Transport。任何情况下不能把内存事件当作持久化事实。

现状：DB 行 + activity_log 是事实，事件总线为内存通知（commit 后 publish，invariant 13 已成立）；持久化 Event Log 表未实现。

17. Storage

17.1 当前选择

单机、单用户场景优先 SQLite。当前不需要为了“企业级”提前切 PostgreSQL。

17.2 Repository 边界

  ↓

业务层禁止在任意位置散落 SQL。Repository 负责领域查询与持久化语义，Store 负责底层数据库实现。

18. Recovery & Idempotency

18.1 Worker Lease

Run 建议具备 worker_id、claimed_at、lease_until。Worker 崩溃后通过 lease expiration 识别 stale run。

规划未实现——现状：单 daemon，restart 时 RecoverStuckRunning 全量恢复 running→queued 重新 claim，已覆盖单机 crash 场景；lease 为多 daemon / 远程 worker 时才需要。

18.2 Daemon Restart

Daemon restart
    │
    ├── load Goals
    ├── recover stale Runs
    ├── requeue eligible Runs
    ├── restore pending Delivery
    └── resume Scheduler

18.3 Idempotency

  • Run claim 必须幂等。
  • Delivery 必须幂等。
  • Event 写入应具备去重/唯一约束能力。
  • Retry 必须创建新的 Run attempt，而不是覆盖历史。

18.4 Watchdog

不要只通过 stdout 无输出判断 Agent 是否死亡。应综合 protocol activity、tool activity、process heartbeat、session heartbeat。

19. Security

当前单机单用户可以保持轻量模型，但一旦支持远程 Runtime，必须引入 Run-scoped Capability。

AgentWork
   │
   └── Run Capability Token
          ├── goal.read
          ├── comment.create
          ├── child_goal.create
          ├── goal.assign
          ├── approval.request
          └── agent.list

GOAL_ID/RUN_ID/AGENT_ID 只能作为上下文标识，不能作为授权凭证。

规划未实现（P1）——现状单机单用户无鉴权，GOAL_ID/RUN_ID 即访问凭证（CLI 直接凭它调 API）；接入远程 runtime（ws/tcp 对外暴露）前必须落地 Run-scoped capability token。

原则：AgentWork 不重新实现 Agent Runtime；OpenAgent-go 也不承担 Goal/Run/Scheduler 等业务编排职责。

24. Architecture Decisions

Decision选择原因
D-001Goal 是 Aggregate Root统一多次 Run、Review、Delivery 的状态权威。
D-002Run 无 Goal 状态权威避免 retry/multi-agent/race 导致状态冲突。
D-003Agent = Runtime + Persona/Capabilities分离“如何连接”和“谁来执行”。
D-004AgentSession 屏蔽协议避免业务层耦合 ACP/JSONL/JSON-RPC。
D-005Workspace 高于 GitWorktree为非 Git 资产预留扩展能力。
D-006Delivery 平台执行Agent 不应决定自己的交付结果。
D-007SQLite 优先当前单机单用户没有 PostgreSQL 的必要性。
D-008不引入 Workflow Engine先用 Goal + dependency + state machine 解决真实需求。
D-009Event Bus 非事实来源保证 daemon crash 后仍可恢复。
D-010Memory 非权威数据库语义记忆用于上下文，不承担业务状态。

25. Roadmap

P0 — 稳定核心闭环

  1. 固化 Goal Aggregate + Reconcile。
  2. 统一 Run Admission。
  3. 完成 AgentSession 抽象。
  4. 打通 Client RPC，尤其 FS / Terminal。
  5. 完善 Run Claim / Lease / Recovery。

P1 — 完善可靠执行

  1. Workspace 抽象。
  2. Delivery Adapter。
  3. Evidence 模型标准化。
  4. Review / Gate 持久化与幂等。
  5. Event Log / Timeline。
  6. Run-scoped Capability。

P2 — 扩展入口与协作

  1. Cron Trigger —— ✓ 已实现（daemon dispatchSchedules + schedule 表）
  2. GitHub/GitLab Issue Trigger —— ✓ 已实现（M4-B：issue poller + webhook，source_ref 链路）
  3. IM Trigger —— ✓ 已实现（M3：notify 入站 + intake processor）
  4. Squad —— ✓ 已实现（leader run + review checkpoint）；Delegation —— 已实现（sub_goal 实体，决策 5-1/6-1，撤销 3-6 的冻结）
  5. Processor Capability —— 部分：compile/intake 已实现；summary/report/analysis 为规划（决策 4-7）

P3 — Memory / Intelligence

  1. Comment Context Compression。
  2. OpenViking 等长期记忆。
  3. Gate Decision Dataset。
  4. Policy Recommendation。
  5. Agent/Goal Health Analysis。

暂不做

  • Temporal/Airflow/LangGraph 式独立 Workflow Engine。
  • 过早迁移 PostgreSQL。
  • 复杂分布式 Scheduler。
  • 让 Agent 自己决定 Delivery。
  • 让 Event Bus 成为状态事实来源。

27. 最终架构原则

AgentWork 的核心不是让更多 Agent 一起工作，而是建立一套可靠的 Agent 工作生命周期。

Trigger
  ↓
Goal
  ↓
Run
  ↓
Admission
  ↓
AgentSession
  ↓
Workspace
  ↓
Execution
  ↓
Verification
  ↓
Evidence
  ↓
Review / Gate
  ↓
Delivery
  ↓
Outcome
  ↓
Event / History
  ↓
Future Context

这条链路构成 AgentWork 的核心闭环。任何新功能都应该回答一个问题：它是在增强 Goal、Execution、Verification、Review、Delivery 这条主链，还是只是外围 Adapter？如果是后者，应尽可能保持与核心领域解耦。
